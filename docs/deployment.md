# Автоматическое обновление BOR через GitHub Actions

## Что уже автоматизировано

- GitHub Actions на `pull_request` и `push main`: тесты Python, синтаксис и сборка Docker.
- GitHub Actions на `main`: тот же проверенный Docker-образ архивируется для развёртывания.
- После включения `BOR_DEPLOY_ENABLED=true` успешные обновления `main` автоматически отправляются на сервер.
- Развёртывание останавливает предыдущий процесс, запускает новый и ждёт проверки Telegram API.
- При неисправности нового образа скрипт пытается вернуть предыдущую версию.
- Данные Docker-volume `bor_data` остаются на месте. Никогда не выполнять `docker compose down -v` без резервной копии.

## Однократная настройка Linux-сервера

Нужны Docker Engine и плагин Docker Compose, `openssh-server`, `gzip`, `flock` (util-linux), исходящее HTTPS к Telegram. Публичный домен и входящий HTTPS **не требуются**, потому что бот использует long polling. На один токен используйте один работающий процесс бота.

1. Создать выделенного пользователя `bor-deploy` и каталог `/srv/bor/releases` с правами записи этого пользователя. Пользователь должен иметь доступ к `docker` (членство в группе `docker` даёт фактически права root; на сервере это нужно учитывать).
2. Создать `/srv/bor/.env` с правами `chmod 600` и строкой `BOT_TOKEN=...`, только **на сервере**. Никогда не добавлять токен в GitHub, чат или Notion.
3. Настроить отдельный ключ SSH только для развёртывания и поместить его закрытую часть в GitHub Actions secret `BOR_DEPLOY_SSH_KEY`.
4. В GitHub `Settings → Secrets and variables → Actions` создать `BOR_DEPLOY_HOST`, `BOR_DEPLOY_USER`, `BOR_DEPLOY_SSH_KEY`, `BOR_DEPLOY_KNOWN_HOSTS`. Последний должен содержать заранее проверенный публичный SSH-ключ **самого сервера**, не результат недоверенного сканирования.
5. Рекомендуется GitHub Environment `production` с ограничением `main` и, на первом запуске, с ручным разрешением развёртывания.
6. Первый раз запустить `Test, build and deploy BOR` вручную (`workflow_dispatch`) из `main` с флажком `deploy=false` — это **только проверки**. После настройки VPS, токена и SSH-секретов запустить повторно с `deploy=true` и проверить запуск `docker ps`, `docker logs bor-bot` и команду `/version` в личном тестовом Telegram-чате.
7. Только после этого задать репозиторную переменную `BOR_DEPLOY_ENABLED=true`. Каждый следующий успешный `push` в `main` обновляет сервер сам.

Для отдельной тестовой версии заведите другого бота в BotFather и раздельный Docker Compose project/volume/каталог. Нельзя использовать один токен параллельно на тестовом и рабочем сервере.

## Откат

Скрипт `scripts/deploy-remote.sh` записывает SHA рабочей версии в `/srv/bor/current-release` **после** успешного проверки контейнера. При неуспешном запуске новой версии автоматически пытается поднять сохранённый Docker-образ и Compose-файл предыдущего выпуска.

Откат кода **не откатывает структуру данных**. При изменении базы сначала делать резервную копию и выпускать совместимые миграции. Пока в первой версии базы данных нет и тестовая карточка хранится в `catalog.json`.

## Безопасность и ограничения

- Сценарий deploy НЕ активен до настройки секретов и включения переменной. GitHub Actions не имеет прямого доступа к рабочему токену бота.
- Не запускайте два контейнера для одного `BOT_TOKEN` одновременно: Telegram long polling конфликтует.
- В проверке готовности выполняется `getMe`: она показывает, что контейнер работает и Telegram отвечает, но **не гарантирует** корректности всех пользовательских функций. После первой установки обязательно вручную проверить `/start`, `/version`, `/start book_demo` и повторный запуск.
- При кратковременной недоступности Telegram новый выпуск может быть ошибочно признан неисправным; старый выпуск сохранён.
- Сборка Docker использует закреплённую прямую зависимость `aiogram==3.31.0`, но зависимости её собственных пакетов могут обновляться; перед критическим выпуском следует внедрить полную фиксацию зависимостей или хэши.
- Не переключать Telegram webhook автоматически: программа сама отказывается запускать polling при уже настроенном webhook, чтобы не уничтожать другую интеграцию.
- Никогда не добавлять `StrictHostKeyChecking=no` и не публиковать файлы `.env`.


## Безопасный ручной запуск проверки

На странице GitHub Actions выберите `Run workflow`, ветку `main` и оставьте `deploy=false` (по умолчанию). Это запускает тесты и сборку, но **не подключается к VPS**. Для первого настоящего развёртывания вручную установите `deploy=true` после заполнения SSH-секретов и тестового токена. Автоматический деплой после push в `main` включается независимо — только если переменная `BOR_DEPLOY_ENABLED` равна `true`.
